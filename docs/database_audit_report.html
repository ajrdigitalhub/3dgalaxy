Executive Summary & Problem Statement

Audit Finding: The provided ER Diagram contains 65 tables, representing an heavily over-normalized legacy relational model. However, an in-depth codebase audit of functions/src and src reveals that 3D Galaxy has already evolved its backend to store rich product attributes in PostgreSQL JSONB columns and centralized dynamic configurations into a cached settings table.

Retaining dozens of dead, unmapped, and duplicate relational tables introduces severe operational and performance liabilities:

Table & Index Bloat

Over 36 unused tables consume database buffer cache, inflate backup times (pg_dump), and force PostgreSQL to update dozens of unused foreign key indexes on writes.

Duplicate Query Loops

Having duplicate tables like product_reviews and customer_reviews forces the backend to run multiple SQL queries and reconcile records in Node.js memory.

Unnecessary Roundtrips

Checking single-tenant tables like warehouses on every order (tx.warehouse.findFirst()) adds needless latency to the checkout critical path.

Category 3: Duplicate & Inefficient Relational Patterns

Case Study A: Review System Duplication (Double Query Bottleneck)

In functions/src/services/reviewAggregation.ts, every product rating calculation executes two concurrent database queries because reviews are split between two tables:

// reviewAggregation.ts Lines 47-62
const customerReviews = await prisma.customerReview.findMany({
  where: { productId },
  include: { customer: { include: { user: true } } }
});

const productReviews = await prisma.productReview.findMany({
  where: { productId, isApproved: true },
  include: { user: true }
});
// Followed by manual array concatenation & sorting in Node.js memory!

Action: Drop product_reviews. Ensure all review workflows write to customer_reviews with an is_approved BOOLEAN column. This eliminates 50% of review query traffic across the storefront.

Case Study B: Warehouse Single-Tenant Overhead

3D Galaxy operates from a single fulfillment facility. In controllers/order.ts and controllers/payment.ts, every single checkout transaction queries:

// controllers/order.ts Line 879 & payment.ts Line 32
const warehouse = await tx.warehouse.findFirst();
if (warehouse) {
  // Associates default warehouse ID on inventory and order records
}

Action: Drop warehouses. Hardcode the default fulfillment location ID or store it in settings. This removes a redundant database query on the payment and order confirmation critical paths.

Category 4 & 5: Settings Consolidation & RBAC Simplification

CMS & Settings Consolidation

The following tables are superseded by the in-memory cached settings table:

  • search_settings ➔ settings.search_settings
  • payment_gateways ➔ settings.payment_gateways
  • theme_settings ➔ settings.theme
  • homepage_section_items ➔ homepage_sections.items JSONB

Settings are cached in Node memory via sysCache (TTL: 30m), reducing database reads to zero for standard page loads.

RBAC Simplification

The ER diagram defines 4 tables: roles, permissions, role_permissions, and user_roles. However, 3D Galaxy uses only three fixed roles: Customer, Admin, and Dealer.

Action: Add a role VARCHAR(20) DEFAULT 'Customer' column to users and drop the 4 RBAC tables. Eliminates a 3-table join on every login, registration, and token refresh.
